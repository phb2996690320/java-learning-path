#### 1. Redis有哪些数据结构？其原理是什么？

**回答：**
Redis支持丰富的数据结构，以满足各种场景的需求。除了最基础的几种，还包括一些高级数据结构和模块。

- **核心数据结构：**
  - **String (字符串):** 最基本的数据类型，是二进制安全的，意味着可以存储任何数据，比如图片或序列化对象。其底层实现是**简单动态字符串 (SDS)**，它相比于C语言原生的`char[]`，具有O(1)时间复杂度获取长度、自动扩容、避免缓冲区溢出等优点。
  - **Hash (字典):** 类似于编程语言中的`Map`，是字段和值的映射表。底层实现有两种：当字段少时使用`ziplist`（压缩列表，一种紧凑的线性结构），节省内存；字段多时转为`hashtable`（哈希表），保证读写效率。
  - **List (列表):** 一个双向链表结构，支持在头部和尾部进行高效的插入和删除操作。底层实现是**quicklist**，它是ziplist和linkedlist的混合体。它将多个ziplist通过双向指针连接起来，既保留了ziplist的内存效率，又拥有链表的高效节点修改能力。
  - **Set (集合):** 是一个无序且元素唯一的集合。底层实现是`intset`（整数集合，当元素全是整数时）或`hashtable`（value为null的哈希表）。
  - **Sorted Set (有序集合):** 类似于Set，但每个元素都会关联一个`double`类型的分数(score)，元素按分数排序且唯一。底层实现是**ziplist**（元素少时）和 **skip list (跳跃表)** 的结合。跳跃表通过多层索引实现了平均O(logN)复杂度的查找、插入和删除，是保证有序集合高效性的核心。
- **高级数据结构：**
  - **HyperLogLog:** 用于做**基数统计**（估算一个集合中不重复元素的个数）。它的巨大优势是，无论存储多少元素，只需要占用**12KB**的固定内存，标准误差仅为0.81%。原理是基于概率论，通过输入元素来估算基数。
  - **Geo (地理空间):** 用于存储和操作地理位置信息，如计算两地距离、查找附近的人等。其底层是使用**Sorted Set**实现的，将二维的经纬度通过**Geohash**算法编码成一维的分数(score)进行存储。
  - **Pub/Sub (发布订阅):** 一种消息通信模式，发送者(pub)发送消息，订阅者(sub)接收消息。它是一个**轻量级的消息队列**，但消息是**非持久化**的，即发即弃。
- **Redis Module (模块):**
  这是Redis的扩展机制，允许用户自定义数据结构与命令，展现了Redis强大的生态和能力。
  - **BloomFilter (布隆过滤器):** 一种概率型数据结构，用于**高效判断一个元素是否一定不存在或可能存在**于某个集合中。它非常节省空间，但有一定的误判率（可能存在）。常用于缓存穿透、爬虫URL去重等场景。
  - **RedisSearch:** 一个强大的全文搜索引擎模块，为Redis提供了二级索引、复杂查询和聚合功能。
  - **Redis-ML:** 支持在Redis内部进行机器学习模型的部署和执行。

**总结：** 回答此问题时，应从基础到高级，并解释关键底层实现（如SDS、跳跃表），这能体现你的深度。提到Module则能展现你对技术前沿的关注。

#### 2. 使用过Redis分布式锁么？它是什么回事？

**回答：**
是的，使用过。Redis分布式锁的核心目标是**在分布式系统中，提供一个全局一致的机制来互斥地访问共享资源**。

- **基础实现：** 使用 `SETNX key value` 命令。该命令只有在`key`不存在时才会设置成功，这符合互斥性。抢到锁后，必须使用 `EXPIRE key seconds` 为锁设置一个过期时间，防止客户端崩溃导致锁永远无法释放，造成死锁。

- **原子性问题：** 您提到的“在`setnx`之后`expire`之前进程crash”的情况是关键问题。这会导致锁无法自动过期。因此，**必须保证设置锁和设置过期时间是原子操作**。

- **正确姿势：** 使用Redis 2.6.12之后版本提供的**增强版`SET`命令**：

  bash

  ```
  SET lock_key unique_value NX PX 30000
  ```

  - `NX`： 等效于`SETNX`，仅当不存在时设置。
  - `PX 30000`： 设置过期时间为30000毫秒。
    这条命令是原子性的，一步到位，解决了原子性问题。

- **释放锁的安全性：** 释放锁时不能简单调用`DEL`，因为可能误删其他客户端持有的锁（例如客户端A阻塞超时后锁被自动释放，然后被客户端B获取，此时A恢复后执行`DEL`就会错误地删除B的锁）。正确的做法是使用Lua脚本，先验证锁的`value`（需要是一个唯一标识，如UUID）是否与当前客户端匹配，匹配成功才删除：

  lua

  ```
  if redis.call("get",KEYS[1]) == ARGV[1] then
      return redis.call("del",KEYS[1])
  else
      return 0
  end
  ```

**总结：** 一个完整的分布式锁答案应包括：`SETNX+EXPIRE`的基础方案 -> 原子性问题 -> 使用原子命令`SET key value NX PX `-> 安全释放锁的Lua脚本方案。

#### 3. 如何找出指定前缀的key？以及Keys指令的问题

**回答：**

- **直接方式：** 使用 `KEYS pattern` 指令，例如 `KEYS user:*` 可以找出所有以`user:`开头的key。
- **Keys指令的问题：** `KEYS`指令在执行时会**阻塞Redis服务器**。因为Redis是单线程处理所有请求，`KEYS`命令会遍历整个数据库中的所有key，如果key数量巨大（如1亿个），会导致服务停顿一段时间（可能长达数秒），对线上业务是灾难性的。
- **解决方案：** 使用 `SCAN` 指令。
  - `SCAN`命令是一个基于游标的迭代器，每次只返回少量元素，因此不会阻塞服务器。
  - 它的语法是 `SCAN cursor [MATCH pattern] [COUNT count]`。客户端需要多次调用`SCAN`，直到返回的游标为`0`，表示迭代结束。
  - **缺点与注意事项：**
    1. **重复可能：** 在整个迭代过程中，如果数据集发生修改（增、删、改），可能会返回重复的key或遗漏某些key。这是为了不阻塞而做出的权衡。
    2. **非原子：** 每次`SCAN`返回的结果只是某个瞬间的一个快照。
    3. **COUNT hint：** `COUNT`参数只是一个提示，返回的数量可能多于或少于它。
  - 最终，**需要在客户端对`SCAN`返回的所有结果进行去重**。

**总结：** `KEYS`会阻塞，绝对禁止在生产环境使用。应使用`SCAN`指令进行无阻塞的渐进式遍历，并在客户端处理重复问题。

#### 4. 使用Redis做异步队列

**回答：**
Redis可以用多种方式做消息队列，各有适用场景。

- **1. 简单队列：** 使用 `List` 结构，通过 `LPUSH` / `RPUSH` 生产消息，另一端用 `RPOP` / `LPOP` 消费消息。
  - **问题：** 如果队列为空，消费者会频繁调用`RPOP`，导致空轮询和CPU浪费。
  - **优化：** 使用 `BRPOP` 或 `BLPOP` 命令，它们是`RPOP`/LPOP`的阻塞版本。当队列为空时，连接会被阻塞，直到有消息到来或超时，从而节省了CPU资源。
- **2. 发布/订阅 (Pub/Sub) 模式：** 用于实现**一对多**的广播模式。一个生产者（发布者）发布一条消息，多个消费者（订阅者）可以同时收到。
  - **优点：** 1:N 快速消息分发。
  - **致命缺点：** 消息是**非持久化**的。如果消费者中途下线，重新上线后无法收到离线期间发布的消息。Pub/Sub的核心是“广播”，而不是“存储转发”，因此**不适合用于重要的、需要可靠积压的消息队列场景**。
- **3. 延时队列：** 使用 `Sorted Set` (ZSET) 实现。
  - **原理：** 将消息内容作为`member`，消息的到期时间戳（如`当前时间+延时时间`）作为`score`。生产者通过 `ZADD` 添加消息。
  - **消费：** 消费者轮询地用 `ZRANGEBYSCORE key 0 <当前时间戳> WITHSCORES LIMIT 0 1` 获取最早到期的一条消息。如果拿到，则处理它并用 `ZREM` 删除，确保消息不被重复消费。

**总结：** 简单小队列用`List`+`BLPOP`；需要广播但可接受消息丢失用`Pub/Sub`；需要可靠延时队列用`ZSET`。对于要求高可靠、持久化、ACK确认的专业需求，应使用RabbitMQ、Kafka等专业消息中间件。

#### 5. 大量key同时过期需要注意什么？

**回答：**
需要避免大量key在同一时刻瞬间过期。

- **问题：** Redis的过期策略是**惰性删除**（使用时检查并删除）和**定期删除**（随机抽取key检查并删除）相结合。如果大量key在同一秒过期，到了那个时间点，定期删除策略可能会集中触发一次删除操作。同时，当客户端请求访问这些已过期的key时，惰性删除也会被触发。这会导致Redis在极短的时间内需要删除大量key，CPU占用会有一个明显的峰值，可能导致应用访问出现短暂的延迟或卡顿。

- **解决方案：** 在给key设置过期时间时，**给过期时间加上一个随机值**，让过期时间点分散开。

  java

  ```
  // 伪代码：将过期时间分散在 24小时 到 24小时 + 随机数 之间
  int expireTime = 24 * 3600 + ThreadLocalRandom.current().nextInt(0, 3600);
  setex(key, expireTime, value);
  ```

  这样可以平滑地处理过期key的删除，避免产生集中式的CPU压力。

**总结：** 集中过期会导致Redis卡顿。解决方案是为过期时间添加一个随机范围值，打散过期时间。

#### 6. Redis如何做持久化？

**回答：**
Redis提供了两种持久化机制：RDB和AOF，通常配合使用。

- **RDB (Redis Database):**
  - **方式：** 在指定的时间间隔生成整个数据集的时间点快照（point-in-time snapshot）。
  - **命令：** `SAVE`（同步，阻塞）或 `BGSAVE`（后台异步）。
  - **原理：** `BGSAVE`的原理是**fork + cow**。
    1. **Fork:** Redis主进程创建一个子进程。
    2. **Copy-On-Write (写时复制):** 子进程与父进程共享内存页。当父进程接收到写请求并要修改某一块数据时，会将被修改页复制一份，子进程的镜像页保持不变。子进程遍历这个不变的内存镜像，将其序列化写入临时的RDB文件。
    3. 替换旧RDB文件。
  - **优点：** 二进制压缩文件，体积小，加载速度快，适合灾难恢复。
  - **缺点：** 会丢失最后一次快照之后的所有数据（不够实时）。
- **AOF (Append Only File):**
  - **方式：** 记录每一次写操作命令到日志文件的末尾。
  - **同步策略 (fsync):**
    - `always`: 每写一条命令都同步到磁盘。最安全，性能最低。
    - `everysec`（默认）: 每秒同步一次。是安全性和性能的折中方案，最多丢失1秒数据。
    - `no`: 由操作系统决定何时同步。性能最好，但最不安全。
  - **优点：** 数据 durability (耐久性) 高，最多丢失1秒数据。
  - **缺点：** AOF文件通常比RDB大，恢复速度慢。
- **重启恢复流程：**
  当Redis重启时，如果同时开启了AOF和RDB，**会优先加载AOF文件**来恢复数据，因为AOF通常数据更完整。流程是：先加载RDB快照基础数据，然后重放AOF日志中的增量写命令。

**总结：** RDB是快照，恢复快但可能丢数据；AOF是日志，安全但文件大。生产环境通常两者都开启。`BGSAVE`的原理是**fork子进程**和**写时复制(COW)**。

#### 7. Pipeline有什么好处？

**回答：**
Pipeline（管道）的主要好处是**极大地提高批量操作的性能**。

- **原理：** 通常的Redis命令是“请求-响应”模式，即客户端发送一个命令后必须等待Redis的回复，才能发送下一个命令。这中间往返的时间（RTT）占据了很大开销。Pipeline允许客户端将多个命令一次性发送给服务器，而无需等待每个命令的回复，最后服务器将多个回复一次性返回给客户端。
- **效果：** 它将N次命令的N次RTT时间，缩减为**1次RTT时间**。这在高网络延迟的环境下性能提升尤为明显。
- **注意：** Pipeline中执行的多个命令之间**不能有逻辑上的依赖关系**（即后一个命令依赖前一个命令的结果）。因为Redis服务器是直接按顺序执行所有命令，在执行过程中不会处理其他客户端的请求。

**总结：** Pipeline通过批量发送命令、一次性读取回复的方式，将多次网络往返延迟压缩为一次，显著提升了批量操作的吞吐量。

#### 8. Redis的同步机制（主从复制）

**回答：**
Redis的主从复制（replication）是数据同步的基础，也是高可用的基石。

- **同步过程（全量同步）：**
  1. **PSYNC：** 从节点启动后，向主节点发送`PSYNC`命令请求同步。
  2. **BGSAVE：** 主节点接收到请求，执行`BGSAVE`生成当前的RDB快照文件，同时用一个**复制缓冲区（replication buffer）** 记录从现在开始收到的所有写命令。
  3. **传输RDB：** `BGSAVE`完成后，主节点将RDB文件发送给从节点。从节点清空旧数据，加载接收到的RDB文件来构建数据。
  4. **缓冲命令同步：** 在主节点发送RDB期间，新的写命令会继续被记录到复制缓冲区。RDB传输完成后，主节点会将缓冲区内的所有写命令发送给从节点。
  5. **命令重放：** 从节点执行这些缓冲的命令，最终达到与主节点一致的状态。
- **增量同步：**
  之后主节点每收到一个写命令，都会**异步地**发送给从节点进行重放，保持最终一致性。
- **从从同步：** 为了减轻主节点的负担，从节点可以作为其他从节点的主节点，形成树状复制结构。

**总结：** 全量同步通过`BGSAVE`RDB文件+**复制缓冲区**实现。增量同步通过异步传播写命令实现。

#### 9. Redis集群

**回答：**
Redis的集群方案主要有两种，目标不同：

- **Redis Sentinel (哨兵)：**
  - **着眼点：高可用 (High Availability)**。
  - **原理：** Sentinel是一个独立的分布式系统，用于监控主从节点。一般由3个或以上Sentinel实例组成集群，它们通过投票机制来判定主节点是否下线（主观下线和客观下线）。当发现主节点故障时，Sentinel会自动从从节点中选举出一个新的主节点，并通知客户端和其他的从节点切换到新的主节点上。
  - **功能：** 监控、通知、自动故障转移、配置提供者。
- **Redis Cluster：**
  - **着眼点：可扩展性 (Scalability) + 高可用**。
  - **原理：** 是真正的分布式解决方案。采用**数据分片（Sharding）** 机制。
    - **分片：** 整个数据集被划分为16384个槽(slot)，每个节点负责一部分槽。
    - **路由：** 客户端可以直接向任意节点发送请求。如果请求的key不在该节点负责的槽范围内，节点会返回`MOVED`错误和正确的节点地址，指引客户端重定向请求。
    - **高可用：** 每个分片实际上也是一个主从复制组，主节点故障后，其从节点会被提升为主节点。
  - **功能：** 数据分片、主从复制、高可用、自动故障转移。

**总结：** **Sentinel**用于在**主从复制**基础上实现**高可用**；**Cluster**用于将数据**分片**，实现**水平扩展**，同时每个分片内部也具备高可用能力。
