## 业务架构

*   架构分类
    

![](<assets/06a6a5b99cedfc699193b442d534e687fd7c8cba.png>)

业务架构是战略，应用架构是战术，技术架构是装备。其中应用架构承上启下，一方面承接业务架构的落地，另一方面影响技术选型。熟悉业务，形成业务架构，根据业务架构，做出相应的应用架构，最后技术架构落地实施。

*   业务架构
    

核心是解决业务带来的系统复杂性，了解客户 / 业务方的痛点，项目定义，现有环境；梳理高阶需求和非功能性需求，进行问题域划分与领域建模等工作；沟通，方案建议，多次迭代，交付总体架构。 

![](<assets/e0500f0030326cc2c3083a89f5f37a3cc3d7d6af.png>)

包括业务规划，业务模块、业务流程，业务事件对整个系统的业务进行拆分，对领域模型进行设计，把现实的业务转化成抽象对象。 在实战中，业务架构的实施包括以下方面：

*   业务流程设计： 对业务流程进行建模和优化，确保业务流程的高效执行和顺畅运转。
    
*   业务规则管理： 定义和管理业务规则，确保业务规则的一致性和灵活性，支持业务的快速变化和调整。
    
*   业务组织架构： 设计和优化组织结构，明确业务部门和角色之间的职责和权限，提高组织的协作效率和业务执行能力。
    
*   横向分层业务，纵向切分模块
    

分层：分层也是我们应对和管理复杂性的基本思维武器，目的是为了解耦。将业务按照层级区分，每个层级为独立的逻辑模块层，每一层专注解决某个领域的问题。下层更抽象，上层更具体 。层级需要有逻辑上的关联，如下层为上层服务或者提供能力支撑。

分模块：是在同一逻辑层中，有哪些独立模块。一个模块代表一个完整的业务或者同类型的业务聚合。每个模块之间相互独立，且模块之间也会存在依赖或者关联。

分功能：在同一个模块内，将独立的功能划分出来，该功能可以代表一个业务入口，简单理解就是一个模块体系中的功能，比较具有代表性，用户比较关注的功能抽象出来。

## 各种技术架构对比

### Hadoop 体系

![](<assets/96a0b1b0dd408c559a544bd0f05b552edb097001.png>)

##### 优点

任务稳定、架构简单, 扩展容易。

##### 缺点

存在离线数仓数据难以更新问题，小文件等常见问题。链路过长、Lama 架构维护成本过高，数据和代码存在两份，离线计算效率低、难以支持实时数仓、OLAP 高并发查询难以支撑。结果集过大时响应效率低。

  

### Hadoop+MPP 体系

![](<assets/1f59a787ebb493652917cfd7ea3a6c5d732934b7.png>)

低成本的存储和 ETL、宽表加工交给 Hive,OLAP 分析，数据应用的对接交给 StarRocks

##### 优点

能够有效的节省存储和计算资源，完美的职责分离与架构解耦。

##### 缺点

依然存在离线数仓数据难以更新问题，小文件等常见问题。难以支持实时数仓，链路过长，**架构复杂性与运维负担，存在一定的**数据冗余与存储成本****。

### MPP 存算一体

![](<assets/20d33c1d52ee97289c3aeae2519a07498f21e157.png>)

##### 优点

链路缩短、批流一体、数据本地化减少网络传输，适合实时分析和高并发查询，延迟可低至毫秒级。

##### 缺点

大规模 ETL 能力欠缺，存储成本高，集群扩展性较低，扩容需数据重分布，时间较久，可能影响服务连续性；存储与计算绑定，资源利用率低。欠缺深度集成数据湖能力。

### MPP 存算分离

![](<assets/8e32a96fa99611767016523b3648bbbbfb61f8b8.png>)

##### 优点

存储成本更低，集群扩展性更好，CN 节点无状态设计，可弹性扩缩容，计算资源与存储解耦。和数据湖的集成更方便。

##### 缺点

依赖缓存命中率，数据延迟稍高些。

### 湖仓一体（数据湖 + Flink）

![](<assets/0051ebb6594db9b1da558a86e0430abcb0d1c21a.png>)

##### 优点

湖仓一体，存算分离，拥有了数据湖的各项能力。

##### 缺点

所有的计算都由 Flink 来完成，内存资源占用过高，OLAP 高并发点查，多位分析和 BI 报表，依然需要一个 MPP 数据库支持。维护的组件过多，增加复杂性。

### 湖仓一体（数据湖 + MPP）

![](<assets/23779af614615e685cf1ac29ffd194c8634b09cc.png>)

##### 优点

*   查询性能提升 通过预计算高频查询场景，将复杂计算结果持久化存储，可将原本需要扫描千亿级数据的查询耗时从分钟级压缩至秒级，显著提高实时分析效率。
    
*   资源隔离与稳定性 支持资源隔离策略，将物化视图刷新任务与实时查询流量分离，避免相互干扰。例如，通过 FE 节点和 CN 节点的混合部署，保障单日业务有效查询数量峰值可达 17 万 / 天，同时确保物化视图刷新成功率稳定在 99.9% 以上。
    
*   灵活的数据分层与扩展 支持分区物化视图，可根据业务需求存储长周期历史数据，结合 Paimon 的数据湖特性，实现数据分层存储和灵活扩展，满足不同时间粒度的查询需求。
    
*   开发成本低 物化视图开发成本低，迭代方便快捷，适合快速交付业务看数需求，并能快速应对业务调整和口径变更。
    
*   存储成本优化 Paimon 作为数据湖存储，支持流批一体处理，存储成本低且扩展性高，结合 StarRocks 的高效查询能力，实现成本与性能的平衡。
    

##### 缺点

*   物化视图管理复杂 需要定期对物化视图进行治理，资源占用过高，包括监控刷新状态、调整刷新参数等。例如，需注意基表分区字段类型对物化视图刷新的影响，避免全表刷新。
    
*   依赖数据模型设计 物化视图的查询改写能力依赖于合理的数据模型设计。若模型设计不合理，可能导致查询无法有效利用物化视图，影响性能。
    
*   系统性风险 需规避一些系统性风险，如基表分区字段为字符串类型时可能导致全表刷新，或物化视图依赖基表分区，基表分区删除时物化视图分区也会被删除。
    
*   UDF 兼容性问题 物化视图定义 SQL 中尽量使用 StarRocks 内置函数，部分 UDF 在物化视图刷新时可能无法兼容，需谨慎使用。
    
*   物化视图数据一致性问题
    

*   基表结构变更影响：若基表的列结构（如删除列）发生变化，物化视图可能失效，但仍可查询，但无法刷新。需及时调整物化视图定义或重建。
    
*   异步刷新延迟：异步物化视图的刷新存在时间窗口，可能导致查询结果与基表数据不一致。需根据业务需求权衡刷新频率与实时性。
    

*   物化视图查询改写限制
    

*   复杂查询支持不足：虽然 StarRocks 支持多表 JOIN、聚合等改写，但在某些复杂场景（如嵌套子查询、特定函数使用）下，可能无法有效利用物化视图改写，需手动优化查询。
    
*   跨数据库或表限制：2.4 版本不支持跨数据库创建物化视图，也不支持基于物化视图的嵌套物化视图，需等待后续版本完善。
    

### 湖流一体（fluss+Paimon+Flink）

![](<assets/0c3eef239143f9b45c0ff96d252682044bc02b75.png>)

##### 优点

1.  数据新鲜度提升
    

*   Fluss 提供秒级数据新鲜度，弥补 Paimon 分钟级延迟的不足，实现流数据实时可见，满足实时分析需求（如实时推荐、风控等）。
    

2.  统一元数据管理与数据分布对齐
    

*   Fluss 通过统一的元数据管理（如 Catalog 同步）和数据分布对齐（Bucket 映射），避免了传统 Lambda 架构中两套存储的冗余和不一致问题。简化开发和运维成本。用户可通过统一接口访问实时和历史数据。
    
*   支持 UNION READ，允许一次查询同时访问实时数据（Fluss）和历史数据（Paimon），实现秒级新鲜度分析。
    

3.  高效的数据更新与查询能力
    

*   Fluss 支持行级更新 / 删除（基于 KV Store）和列式裁剪，相比 Kafka 更适合实时分析场景。
    
*   列式存储格式（Apache Arrow）结合压缩（ZSTD/LZ4）显著降低网络传输和存储成本，列裁剪性能提升 10 倍。支持流式列裁剪与流式分区裁剪。
    

4.  Delta Join 优化资源消耗
    

*   Fluss 与 Flink 的 Delta Join 算子结合，通过异步点查减少状态大小，资源消耗降低 10 倍（如淘宝作业从 2300 CU 降至 200 CU）。
    
*   支持多作业并发更新宽表，避免 Paimon 的单 Writer 限制。
    

5.  兼容性与扩展性
    

*   后续 Fluss 支持多种数据湖格式（如 Iceberg、Hudi），未来可扩展其他计算引擎（如 Spark、StarRocks），适应不同场景。
    

6.  湖流一体的成本与效率平衡
    

*   热数据（秒级延迟）存储在 Fluss，冷数据（分钟级延迟）归档至 Paimon，存储成本降低 90%。
    
*   流式读写与批式分析无缝衔接，避免重复计算链路。
    

7.  弹性无状态服务
    

*   Fluss 0.7 将入湖服务重构升级成了一个弹性无状态服务。在设计上，一方面是无状态化，不再使用 Flink State 存储同步位点，而是将位点信息持久化在 Fluss 元数据中，并计划在下一版本中持久化到 Paimon v1.2 引入的快照属性中。另一方面是微批处理模型，Flink 作业不再持续订阅所有表，而是每次只处理一张表，处理完成后再主动请求下一个待同步的表，这有效降低 Fluss 端的连接压力和资源消耗，同时提升了攒批效率和吞吐表现。
    

##### 缺点

1.  技术成熟度
    

*   Fluss 仍处于快速发展阶段，部分功能（如多模态数据支持、Kafka 协议兼容）尚未完全成熟，需持续关注社区更新。
    

2.  运维复杂度
    

*   湖流一体架构涉及多个组件（Fluss、Paimon、Flink，StarRocks），需协调配置和维护，对运维团队要求较高。
    

3.  成本考量
    

*   Fluss 热数据存储成本高于 Paimon，需合理规划数据分层策略，平衡实时性和成本。
    
*   实时链路与历史链路的资源分配需精细调优，否则可能引发资源争用。
    

4.  生态兼容性
    

*   Fluss 目前仅支持 Paimon 作为湖存储，未来需扩展至 Iceberg、Hudi 等格式。
    
*   部分功能（如 Schema 演进、系统表查询）仍在开发中，生产可用性需验证。
    
*   部分场景需适配现有工具链，如数据探查、可视化工具对 Fluss 的支持可能有限。
    

5.  性能瓶颈
    

*   Fluss 依赖本地磁盘存储热数据，扩展性受限于硬件资源。
    
*   大规模数据回溯时，仍需依赖 Paimon 的批处理能力，时效性受限。

##### RisingWave 使用场景：

1.  实时 ETL 与数据管道
    

*   对比传统工具如 Flink，用 SQL 简化流程
    
*   支持多数据源和物化视图
    

2.  实时分析与监控
    

*   亚秒级延迟，适用于金融、物联网
    
*   复杂查询和窗口函数
    
*   实时高并发点查
    

3.  事件驱动应用
    

*   实时告警、欺诈检测
    
*   多流 join 打宽处理复杂逻辑
    

4.  特征工程与机器学习
    

*   实时特征构建和拼接
    
*   支持 SQL 和 UDF
    

5.  CDC 数据集成
    

*   数据库变更捕获，统一数据视图
    

##### 优点：

*   统一的流数据管道
    
*   PostgreSQL 兼容性
    
*   高效流表 join
    
*   使用独立查询节点优化性能。将数据查询（以及批式数据写入）与流式数据写入处理隔绝。
    
*   支持秒级自动扩展，无须人工干预即可应对不同工作负载。
    
*   全面流式 SQL
    
*   自动变更数据模式
    
*   时间旅行查询
    
*   架构简单，运维组件更少。
    

##### 缺点：

*   没有可编程接口 RisingWave 不提供 Java 和 Scala 等语言的底层应用接口，用户也无法手动管理内部状态（除非你想黑进去！）。如需使用 Java、Scala 和其他语言编码，请考虑使用 RisingWave 的用户定义函数（UDF）。
    
*   不支持事务处理 RisingWave 不支持事务型工作负载，因此无法替代专用于事务处理的操作型数据库。不过，它支持只读事务，可确保数据的新鲜度和一致性。它还能理解上游数据库变更数据捕获（CDC）的事务语义
    
*   不适合状态管理或复杂流处理逻辑（CEP）
    
*   不适合非结构化数据处理。
    
*   不适合大规模元数据管理。RisingWave 使用 PostgreSQL 管理元数据，适合中等规模（百万级）元数据场景。对于十亿级及以上元数据量级和高并发访问需求，建议选择分布式元数据管理方案（如 FoundationDB、Cassandra）。

3.  服务可扩展：如何对外提供低延迟的 API 服务，支持百万级并发访问？
